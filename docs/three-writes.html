JJCon · building developer tools on jj-lib

Three writes, not one:
files · workspace state · git refs

Transaction::commit writes only the op log — the view, the operation, and the op-heads swap. The files on disk, the workspace's record of where it is, and the colocated .git are three separate writes that jj-lib leaves entirely to you. The jj CLI performs them silently around every command; a tool built on jj-lib must reimplement them, in the right order, or the repo drifts apart.

01 · Anatomy of one command

Every mutating gt command ends with the same choreography. The order is load-bearing — and it is not the order the writes are numbered in:

write ③ · git refs
git::reset_head → git::export_refs

On tx.repo_mut(), before commit — export mutates the view’s record of what git holds, so it must land in the same operation.

the op log
tx.commit(description)

Writes the view blob, the operation, the index, and swaps op heads. Touches nothing else — provably: transaction.rs imports no workspace or git module.

write ① · files
locked_wc.check_out(&new_wc)

Diffs old tree → new tree and rewrites the worktree. Skipped bytes-for-bytes when trees match — but never skip the call.

write ② · workspace state
locked_ws.finish(repo.op_id())

Persists “this workspace is at operation X, tree Y”. The op id must be the new one — the old id silently re-records staleness.

02 · What each gt command writes

commandoperationsgit refsfileswc statenetwork
gt init3 — workspace · import refs · import head HEAD reset reset (state only) adopt HEAD—
gt checkout1–2 — snapshot? · checkout HEAD follows @ tree swap —
gt create1–2 — snapshot? · create new refs/heads/* no-op (same tree) —
gt modify2 — snapshot · amend branch ref moves if conflicts materialize —
gt submit1–2 — snapshot? · push refs/remotes/* move — push + PR API
gt sync1–2 — snapshot? · fetch+restack branches rewritten restacked @ fetch

“snapshot?” = write zero: folding dirty files into @ is its own operation, committed before the command even starts. In a colocated repo write zero also imports git’s own writes — import_head before the snapshot (a raw git commit moved HEAD and the files), import_refs after — or external git activity silently corrupts the fold. And even a push or a fetch is an op-log write, because it moves remote-tracking bookmarks in the view.

03 · Skip a write, get a broken repo

skip ① check_out

The op log says @ moved; the disk still shows the old tree. The next snapshot absorbs the difference into the wrong commit — silent history corruption.

skip ② finish

The workspace still records the old operation. Every later command opens with “stale working copy” — this is exactly what WorkingCopyFreshness::check_stale exists to catch.

skip ③ export_refs

jj bookmarks and .git/refs/heads silently diverge. git log lies to the user; the next import surfaces the drift as ref conflicts.

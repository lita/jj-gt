01 · jj-lib

Why build on jj-lib?

  • Build your own interface.
    Repository APIs work in a GUI, TUI, or server. A good fit for our Tauri app.
  • Ship jj's capabilities inside your tool.
    Users don't need the jj executable. Git fetch and push still use the git binary.
  • Choose what your commands mean.
    You decide how "commit" and "undo" behave. jj-lib provides the building blocks.
  • Use jj-cli as a reference implementation.
    There's limited scaffolding. Read how jj connects the pieces, then adapt it to your tool.

01 · jj-lib

What jj-lib handles, and what you handle

  • jj-lib owns repository logic.
    Commits, trees, revsets, transactions, and working-copy APIs.
  • Your tool owns the user experience.
    jj-cli supplies terminal I/O and config loading. jj-lib provides config types and defaults; your app chooses how to load them.
  • Storage is replaceable.
    Commit storage, operation storage, and indexes have backend interfaces. Git is one implementation; you can supply another.
  • Repository changes go through transactions.
    Load the repo at an operation, change its view, then publish a new operation.
  • Repo state and files on disk are separate — and you must handle when they sync!
    The repo records the intended working-copy commit; snapshot and checkout synchronize it with actual files — and that's your job.
    Git colocation adds one more state — 3 separate states you must manage.

02 · the model

Two histories, one working copy

A Workspace connects a working copy to the shared repo. The View records its target commit; .jj/working_copy records the last synchronized tree and operation.

1 · repo view + operation history 2 · working-copy files + recorded state 3 · Git refs, HEAD, index

02 · transactions

Creating a commit: snapshot, then transact

// Sketch: load and reconcile before snapshotting.
let repo = ws.repo_loader().load_at_head().block_on()?;
// …adopt Git HEAD; lock and check WC freshness…
// …reload the repo if the WC is ahead…

let (wc_tree, _) = locked_ws.locked_wc()
    .snapshot(&opts).block_on()?;
// …record changed @ in a snapshot operation…
// …finish WC state; use the updated repo below…

// Build the command's transaction.
let mut tx = repo.start_transaction();
let c = tx.repo_mut()
    .new_commit(vec![parent_id], wc_tree)
    .set_description("feat: add users")
    .write().block_on()?; // stores the commit object

// Publish the new repository state.
let repo = tx.commit("create").block_on()?;
  • Capture file edits before acting on @.
    @ is the working-copy commit. Snapshotting records the files selected by your tracking and ignore rules.
  • Save the snapshot as a separate operation.
    Pre-command edits stay recoverable. Your undo policy decides whether to keep them checked out or restore an earlier state.
  • Store objects; keep the View private.
    A commit points to a whole tree. Objects can be written immediately; publication makes the updated View current.
  • commit() publishes repo state.
    It writes the View, operation, and index, then updates operation heads. File checkout and Git synchronization are separate steps.

02 · concurrency

Concurrent transactions and async APIs

Concurrent operations can be merged

  • Transactions build independent Views. Concurrent writers can publish two operation heads.
  • load_at_head() reconciles divergent heads with a three-way merge of Views.
  • Conflicting ref updates are recorded. Move a bookmark two different ways and it can appear as main??.
  • Some steps still lock: working-copy mutation, operation-head updates, and parts of the Git backend. The op-heads lock reduces duplicate reconciliation.

Async APIs can still do blocking work

use pollster::FutureExt as _;

let repo = ws.repo_loader()
    .load_at_head().block_on()?;
let c = builder.write().block_on()?;
tx.repo_mut().rebase_descendants().block_on()?;
let repo = tx.commit("…").block_on()?;
  • pollster waits on the current thread. jj uses it internally, too.
  • Some futures are !Send: they must stay on one thread and cannot go directly into tokio::spawn.
  • For a Tauri or Tokio app: create and run the jj workflow inside spawn_blocking, using pollster there.
  • Local backends still do synchronous I/O. export_refs, push_refs, and GitFetch::fetch are synchronous APIs.

The lock-free concurrency design covers repository operations. File edits need a snapshot. Dropbox/NFS syncing has documented Git-backend corruption and bookmark-loss risks.

03 · jj-gt

Putting it together: stacked PRs on jj-lib

Graphite (gt) builds stacked PRs on Git: one branch per PR, based on the branch below it. jj-gt implements that workflow with jj-lib.

CommandGraphite (gt)jj-gt
init Configure trunk; store branch metadata in refs/branch-metadata/* Initialize a colocated jj workspace; import Git refs and HEAD
checkout main Switch to the main branch Create a fresh, empty @ on top of main
create Create a branch and commit; ~27 Git subprocesses in the recorded trace* Describe @, bookmark it, create a new @; one operation + a snapshot if needed
submit Push branches; create or update PRs through Graphite Push with leases; call GitHub directly; record updated remote bookmarks in an operation
sync Restack branches that merge cleanly; leave conflicted branches for later Fetch and restack in one transaction; persist conflicts; check out once at the end

*gt 1.8.6 with --debug; counts depend on repository state. Graphite command reference.
jj-gt may record extra snapshot/import operations. Undo restores jj state and files; GitHub changes and app metadata are separate.

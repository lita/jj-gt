01 · jj-lib

Why build on jj-lib?

  • The primitives don't assume a terminal — a great use case for us, a Tauri app.
    And they can be used with different backends, not just Git — though you would have to implement that integration.
  • Your end user does not have to install jj to use your developer tool.
    jj's capabilities ship bundled inside your tool — no jj executable required (git network ops still shell out to the git binary).
  • You define what commands are — what "commit" means, what "undo" means, for your tool.
    jj-lib gives you the primitives; the command semantics are yours to shape.
  • Not a lot of scaffolding — but jj-cli is open source.
    Leverage it as the reference implementation: read what jj itself does, then copy it or diverge.

01 · jj-lib

jj-lib vs jj-cli

  • jj-lib owns repository logic.
    Rust APIs for commits, trees, revsets, transactions, and working copies — designed for any TUI/GUI to leverage. But not much scaffolding.
  • jj-cli owns the user input/output and overall UX.
    Terminal I/O and config discovery live there (jj-lib ships the config types + defaults). Your integration supplies its own interface and loading policy.
  • Storage is replaceable.
    Commit storage, operation storage, and indexes sit behind backend interfaces. Git is one commit backend.
  • Repository changes go through transactions.
    Read a repo at an operation, modify its view, then commit a new operation to the log.
  • Repo state and files on disk are separate — and you must handle when they sync!
    The repo records the intended working-copy commit; snapshot and checkout synchronize it with actual files — and that's your job.
    Git colocation adds one more state — 3 separate states you must manage.
    Why: jj's lock-free design (the git backend still has locks). Racing operations can't lose repo state — collisions surface as conflicts in the op log. File edits are captured only when snapshotted.

02 · the model

A Workspace = your working copy + a handle to the shared repo. The View records which commit should be checked out; .jj/working_copy records what is.

state 1 · repo — .jj/repo (op log + commits) state 2 · working copy — files + .jj/working_copy anchor state 3 · colocated .git — refs, HEAD, index

02 · transactions

Creating a commit: snapshot, then transact

// 0 · snapshot FIRST — the disk may have changed
//     from other sources (editor, raw git, agents)
let (wc_tree, _) = locked_ws.locked_wc()
    .snapshot(&opts).block_on()?;   // wc_tree = the files on disk,
                                    //   as one content-addressed tree
// …if the tree changed: fold it in, as ITS OWN operation…

// 1 · read the repo at an operation
let repo = ws.repo_loader().load_at_head().block_on()?;

// 2 · transaction: mutate the in-memory View
let mut tx = repo.start_transaction();
let c = tx.repo_mut()
    .new_commit(vec![parent_id], wc_tree)  // content IS this tree (not a diff)
    .set_description("feat: add users")
    .write().block_on()?;

// 3 · commit = write the operation + publish
let repo = tx.commit("create").block_on()?;  // repo state only
  • Snapshot before every command.
    The working copy is a commit (@), but the disk is its source of truth — fold disk → @ first, so your command never operates on a stale @. (A policy, not a law: jj's --ignore-working-copy is the opt-out.)
  • The snapshot is its own operation.
    Pre-command edits become durable and recoverable. Your undo policy decides whether they stay checked out — jj undo keeps them; jj-gt undo rewinds the whole command group, reversibly.
  • A transaction edits the View in memory.
    Commit/tree objects may hit the store immediately — but they're invisible: the view stays private until publish. Files, workspace state, git refs: untouched.
  • commit() = write view + operation + index, then publish.
    An atomic op-heads swap. Still not written: your files, your workspace state, your git refs — that choreography is the next slides.

02 · concurrency

Lock-free concurrency — and async everywhere

Concurrent edits are safe by design

  • No repo-wide lock file: jj accepts that concurrent changes can always happen — two writers just leave two op heads
  • The next load_at_head() merges them automatically — a three-way merge of Views ("reconcile divergent operations")
  • Collisions become data, not corruption: a bookmark moved by both sides shows as a conflicted ref (main??); operations are immutable, so repo state survives — even syncing a clone over rsync/Dropbox/NFS (with documented git-backend caveats)
  • Locks that do exist: the working-copy lock (one mutator of the files), a short op-heads lock ("not needed for correctness" — it just avoids duplicate reconciliation), and the git backend's own

…and nearly every call is async

use pollster::FutureExt as _;

let repo = ws.repo_loader()
    .load_at_head().block_on()?;
let c = builder.write().block_on()?;
tx.repo_mut().rebase_descendants().block_on()?;
let repo = tx.commit("…").block_on()?;
  • pollster is what jj-lib itself uses — a tiny park-this-thread crate driving its own internals
  • Core traits (Repo, WorkingCopy) return !Send futures — don't plan on tokio::spawn; block on the current thread
  • In an async app (Tauri, tokio): run jj-lib inside spawn_blocking, pollster within — never park a runtime thread
  • Today the async is largely a facade over sync I/O (built for future cloud backends); still sync: export_refs, push_refs, fetch

docs/technical/concurrency.md — jj's own writeup of the lock-free design (and the git backend caveat, jj#2193).

03 · jj-gt

Putting the pieces together: Graphite, on jj-lib

Graphite (gt) is a wrapper around git for stacked PRs — one branch per change, each PR based on its parent. I reimplemented it on jj-lib: jj-gt.

original gtjj-gt — on jj-lib
jj-gt init stack metadata smuggled into refs/branch-metadata/* colocate .jj onto .git; import refs + HEAD
jj-gt checkout main git switch main fresh empty @ on top of main
jj-gt create ~27 git subprocesses (traced: gt 1.8.6 --debug): stash fingerprint, detached commit, switch -c describe @, bookmark it, new @ on top — 1–2 operations
jj-gt submit push + PRs via Graphite's server (repo must be synced with their app) force-with-lease push + GitHub API directly — a push is an operation too
jj-gt sync checkout + rebase per branch; conflicted branches wait for you — git can't persist a conflicted commit one transaction: fetch → restack in memory; conflicts are data, restack always completes; one checkout — locally undoable

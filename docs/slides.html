01 · jj-lib

jj-lib is the engine, not the car

  • jj-lib owns repository logic.
    Rust APIs for commits, trees, revsets, transactions, and working copies. Designed for any TUI/GUI to leverage — but it does not have much scaffolding.
  • jj-cli owns the user input/output and overall UX.
    Terminal I/O and user configuration live there. Your integration supplies its own interface and configuration.
  • Storage is replaceable.
    Commit storage, operation storage, and indexes sit behind backend interfaces. Git is one commit backend.
  • Repository changes go through transactions.
    Read a repo at an operation, modify its view, then commit a new operation to the log.
  • Repo state and files on disk are separate — AND THEY MUST BE SYNCED.
    You, as the library user, must handle syncing between repo state and what is on disk. The repo records the intended working-copy commit; snapshot and checkout synchronize it with actual files.
    With git colocation, .git is one more state you own — that is 3 separate states you must manage.

crates.io: jj-lib = "0.45.1" — a 0.x crate; APIs move every release. Pin it.

01 · jj-lib

The power — and the price

the power

One engine for GUIs, TUIs, and custom CLIs alike — and because it's a library, your users never have to install jj. The full jj capability set — op log, rebase machinery, conflict handling — ships bundled inside your devtool, in one binary.

the price

That power is not free. As the last slide said: not much scaffolding — and the state (repo · files on disk · colocated .git) is yours to keep in sync, on every command.

the payoff

A user experience git tooling can't easily match: no data loss (every state change lands in the op log — undoable), first-class conflicts (they materialize as data instead of blocking), and good error handling (staleness detected, concurrent writes merge safely).

02 · state

Colocated = four stores to keep honest

.jj/repo

The jj data model. Op log (operations + views), op heads, commit backend — in colocated repos, a pointer at .git's objects (git_target) plus change-id sidecar.

written by: Transaction::commit

.jj/working_copy

Workspace state. checkout: which operation the files correspond to (75 bytes — the staleness anchor). tree_state: which tree, plus a per-file stat cache.

written by: LockedWorkspace::finish(op_id)

worktree

Your files on disk. The source of truth for @'s content — but the repo only learns about edits when someone snapshots.

written by: LockedWorkingCopy::check_out

.git/

Git's copy of the truth. refs/heads/*, HEAD, the index. Colocation means this is now yours to maintain — import their writes, export yours.

written by: git::export_refs · git::reset_head

Four stores, four writers, zero automatic synchronization. Every gt command reconciles all four.

02 · state

.jj/working_copy: "should be" vs "is"

$ ls .jj/working_copy
checkout     ← operation id + workspace name  (the staleness anchor)
tree_state   ← current tree id + sparse patterns + per-file stat cache
type         ← "local" (which working-copy backend)

The op store's own docs, on wc_commit_ids:

"The commit that should be checked out … the working copy (.jj/working_copy/) has the source of truth about which commit is checked out."

  • Every command starts by comparing checkout's op id against the op head — WorkingCopyFreshness::check_stale
  • Equal → Fresh · behind → stale working copy — someone wrote the op log without writes 1+2
  • The stat cache is why snapshots are fast — and why finish() runs even when nothing changed

02 · transactions

A transaction commits one write

let mut tx = repo.start_transaction();
tx.repo_mut()…                        // mutate the in-memory view: new commits,
                                      // bookmarks, wc pointer, rebases
tx.repo_mut().rebase_descendants().block_on()?;   // forget this → panic
let repo = tx.commit("gt create …").block_on()?;  // writes: view + operation
                                      //         + index + op-heads swap
  • commit() returns a new Arc<ReadonlyRepo> — the old one is stale; its op_id() feeds write 2
  • It does not touch your files, your workspace state, or your git refs

Receipt: transaction.rs imports no working-copy, workspace, or git module. The three writes aren't skipped — they're not reachable from here.

02 · snapshots

Snapshot: write zero, before every command

The working copy is a commit (@). The disk is its source of truth — until someone folds the disk back into it.

  • When: at the start of every command — even gt log. Skip it and everything sees a stale @
  • How: take the wc lock → check_stale → walk the disk (stat cache) → if changed, rewrite_commit(&wc).set_tree(…) in its own operation → finish(op_id) — always
  • Why its own operation: undoing the command keeps your edits; a crash mid-command loses nothing
  • Colocated bonus: write zero also means adopting git's writes — import_head before the snapshot, import_refs after. One raw git commit is otherwise silently mis-folded, forever

03 · the real gt, traced (gt --debug, v1.8.6)

What Graphite has to build on plain git

gt create27 git subprocesses
re-derive all state — for-each-ref ×2 · show-current ×3 · rev-parse ×4…→ stash create→ temp index + write-tree ×2→ add --all→ switch -d main→ commit→ switch -c 09-09-feat_…→ write refs/branch-metadata/* (parent: main)

on jj-lib: 2 operations — snapshot, create. The view already knows every branch and parent.

gt submit13 subprocesses before any network
re-derive all state — again, from zero→ api.graphite.com /is-repo-synced→ push + PRs, mediated by Graphite's server

on jj-lib: push_refs (one git spawn, force-with-lease) + GitHub API directly — and the push is itself an operation.

gt sync13 subprocesses before any network
re-derive all state — again→ api.graphite.com /pull-request-info→ fetch trunk · delete merged · restack every branch (worktree thrash)

on jj-lib: fetch + in-memory restack + one checkout, in one operation — one gt undo away.

Every gap is a jj-lib primitive Graphite had to hand-roll: no op log → re-read the world each run; no view → stack parents smuggled into refs/branch-metadata/*; no snapshot → stash create + a temp index + write-tree to fingerprint the worktree.

fin

Take these home

  • tx.commit() is one write of four — files, workspace state, and git refs are yours, in that load-bearing order: ③ · commit · ① · ②
  • Snapshot at the top of every command, as its own operation — and always finish()
  • Colocated repos: import git's writes too (HEAD before, refs after), or one raw git commit wedges you
  • Steal the choreography from cli_util.rs — it's the reference implementation of everything jj-lib won't do for you
  • The op log pays for all of it: concurrency, staleness detection, and undo in 100 lines

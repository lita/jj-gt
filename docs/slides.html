01 · jj-lib

jj-lib is the engine, not the car

The architecture is deliberate: the CLI is just one consumer. TUIs, GUIs, CI shims, IDE integrations — all meant to build on the same library.

  • Commit store — content-addressed commits/trees/files (git-backed in colocated repos)
  • The op log — every repo view change is an immutable, mergeable operation
  • Rewrite machinery — content-aware rebase, descendant tracking, conflicts as data
  • Revsets — programmatic graph queries, no parser required
  • Working-copy engine — snapshot & checkout with a stat cache
  • Git interop — import/export refs, fetch/push via the real git binary

crates.io: jj-lib = "0.45.1" — a 0.x crate; APIs move every release. Pin it.

01 · jj-lib

…and it is deliberately bare-bones

  • No user I/O — no terminal, no prompts, no output formatting
  • No config discovery — StackedConfig exists, but you assemble the layers
  • No per-command glue — nothing snapshots, checks out, imports or exports automatically
  • No undo — the op log makes it possible; the command is CLI code

grep export_refs in jj-lib: zero callers outside git.rs.
Nothing writes your git refs unless you do.

01 · jj-lib

Bare-bones is a feature

  • The primitives don't assume a terminal: the same library powers a CLI, a Tauri GUI, a CI bot, a Graphite clone
  • You choose the choreography — which writes, when, and what "a command" even means for your tool
  • And you're not guessing: the jj CLI is the reference implementation of the scaffolding

Treasure map: cli/src/cli_util.rs — WorkspaceCommandHelper is every hidden step the CLI performs around your command. When in doubt, read what jj itself does, then decide to copy it or diverge.

02 · state

Colocated = four stores to keep honest

.jj/repo

The jj data model. Op log (operations + views), op heads, commit backend — in colocated repos, a pointer at .git's objects (git_target) plus change-id sidecar.

written by: Transaction::commit

.jj/working_copy

Workspace state. checkout: which operation the files correspond to (75 bytes — the staleness anchor). tree_state: which tree, plus a per-file stat cache.

written by: LockedWorkspace::finish(op_id)

worktree

Your files on disk. The source of truth for @'s content — but the repo only learns about edits when someone snapshots.

written by: LockedWorkingCopy::check_out

.git/

Git's copy of the truth. refs/heads/*, HEAD, the index. Colocation means this is now yours to maintain — import their writes, export yours.

written by: git::export_refs · git::reset_head

Four stores, four writers, zero automatic synchronization. Every jj-gt command reconciles all four.

02 · state

.jj/working_copy: "should be" vs "is"

$ ls .jj/working_copy
checkout     ← operation id + workspace name  (the staleness anchor)
tree_state   ← current tree id + sparse patterns + per-file stat cache
type         ← "local" (which working-copy backend)

The op store's own docs, on wc_commit_ids:

"The commit that should be checked out … the working copy (.jj/working_copy/) has the source of truth about which commit is checked out."

  • Every command starts by comparing checkout's op id against the op head — WorkingCopyFreshness::check_stale
  • Equal → Fresh · behind → stale working copy — someone wrote the op log without writes 1+2
  • The stat cache is why snapshots are fast — and why finish() runs even when nothing changed

02 · transactions

A transaction commits one write

let mut tx = repo.start_transaction();
tx.repo_mut()…                        // mutate the in-memory view: new commits,
                                      // bookmarks, wc pointer, rebases
tx.repo_mut().rebase_descendants().block_on()?;   // forget this → panic
let repo = tx.commit("jj-gt create …").block_on()?;  // writes: view + operation
                                      //         + index + op-heads swap
  • commit() returns a new Arc<ReadonlyRepo> — the old one is stale; its op_id() feeds write 2
  • It does not touch your files, your workspace state, or your git refs

Receipt: transaction.rs imports no working-copy, workspace, or git module. The three writes aren't skipped — they're not reachable from here.

02 · snapshots

Snapshot: write zero, before every command

The working copy is a commit (@). The disk is its source of truth — until someone folds the disk back into it.

  • When: at the start of every command — even jj-gt log. Skip it and everything sees a stale @
  • How: take the wc lock → check_stale → walk the disk (stat cache) → if changed, rewrite_commit(&wc).set_tree(…) in its own operation → finish(op_id) — always
  • Why its own operation: undoing the command keeps your edits; a crash mid-command loses nothing
  • Colocated bonus: write zero also means adopting git's writes — import_head before the snapshot, import_refs after. One raw git commit is otherwise silently mis-folded, forever

A "read" command still writes

write (create, sync…)read (log, ops)

Even a fetch or a push is an op-log write — they move remote-tracking bookmarks in the view.

fin

Take these home

  • tx.commit() is one write of four — files, workspace state, and git refs are yours, in that load-bearing order: ③ · commit · ① · ②
  • Snapshot at the top of every command, as its own operation — and always finish()
  • Colocated repos: import git's writes too (HEAD before, refs after), or one raw git commit wedges you
  • Steal the choreography from cli_util.rs — it's the reference implementation of everything jj-lib won't do for you
  • The op log pays for all of it: concurrency, staleness detection, and undo in 100 lines
